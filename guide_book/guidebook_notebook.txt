# 特別支援教育におけるWebアプリケーション開発の実際

【本ハンドブックの目的】
知的障害や発達障害を伴う児童生徒が、余計な操作の負担なく学習そのものに没頭できるようにするためのUI/UX設計指針と、学校現場で絶対に破綻させないための開発・運用ノウハウをまとめた実践書です。

## 📚 理論・設計各章

教育的背景や認知特性から、言葉に頼らない構造化、学校の制約への対策までを詳しく解説しています。

[第1章]
### 生成AIで拓く教育アプリの4大領域

ドリルアプリにとどまらず、授業提示用、課題プリントの自動生成、教員の校務効率化まで多角的に展開する意義を整理します。

[第2章]
### 学習アプリの5大メリットと具体物との使い分け

具体物教材と対比しながら学習アプリの5大メリットを整理し、概念の基礎形成における有効性（仮説）と具体物との役割分担を解説します。

[第3章]
### アプリでの学習は、強化学習と似ている？

AIの強化学習（試行錯誤と報酬・ペナルティ）を手がかりに、子供が活動ルールや概念を掴むプロセス、適切な難易度調整と「強化」の視点を解説します。

[第4章]
### 学習用アプリの設計・実装思想

目的の明確化から、ドラッグ・タップの操作性、非言語的な画面構成、端末特性への防衛、ノイズ除去、AIの悪癖への対処まで、現場の実装ノウハウを体系化します。

### Geminiを活用したアプリ作り　プロンプトについて

第4章までの設計思想を落とし込んだコピペで使えるマスタープロンプト、追加機能（アイコン・IndexedDB・JSON共有）、各指示の教育的・技術的な解説をまとめます。

# 第1章：生成AIで何ができる？

生成AIの最も効果的な活用方法は、プログラミングだと考えています。その中でもHTML、CSS、Javascriptを使用したアプリ開発は、環境の構築を一切必要とせず共有も容易なため、学校現場にとって最も合理的な方法だと思っています。そこで、本ページでは生成AIを活用したアプリ作りについて説明します。生成AIを活用すれば、児童生徒が手元で操作する学習用アプリにとどまらず、視覚支援等の授業で活用するアプリ、プリント課題の作成アプリ、そして教員自身の校務効率化アプリまで作成することができます。それぞれの例や意義を紹介します。

### 📌 この章の要点一覧（概要）

・学習用アプリにとどまらない視野：特別支援の現場の課題は児童生徒の個別学習だけではありません。授業支援、教材作成、校務までを包括して捉える視点も大切です。その他にも、発想次第で活用の幅は広がります。
・学習用アプリ：児童生徒が使用し、概念獲得や記憶の定着を促進する個別最適化教材です。
・授業支援アプリ：電子黒板や大型モニターに映し、主に視覚支援を行うことで授業を円滑に進めるためのツールです。
・プリント課題作成アプリ：児童生徒の実態に合わせた難易度のプリント教材を自動生成・印刷するアプリです。
・業務効率化アプリ：指導計画の作成、アセスメント、分掌業務等を支援する実務ツールです。
・その他：アプリの作成以外にも、既存のExcelファイルに数式を加えて自動化したり、Power Automate等の業務効率化ツールの活用に役立てたりすることもできます。

## 1.1 アプリ開発の視野を広げる「4つの領域」の実際

教育現場においてプログラミングや生成AIを活用しようとするとき、多くの教員は「児童生徒が使うタブレットドリル」を作ろうとします。それが最も効果的であると考えますが、業務改善の推進が求められる昨今、より広い視野でアプリの役割を定義する必要があります。

現場で求められる業務は幅広く、授業関連では教材作成（具体物、プリント等）、指導計画の作成等、分掌業務ではクリエイティブな内容からコピペで終わる単純作業まで様々です。これらのすべてをアプリで効率化するという考えは非効率ですが、効率化を検討すること自体は重要です。また、短期的な視点で考えると、現状のやり方を継続するのが効率的であることは否定できませんが、長期的な視点や引き継ぎ等を踏まえると、生成AIを活用してアプリを作成することが効率的となる可能性もあります。

ただし、質の低いアプリは逆効果ということも頭に入れておく必要があります。

本ページでは、開発対象を以下の4つの領域に分類し、それぞれの役割に応じた最適な設計を提案します。

### 1. 学習用アプリ（個別学習・概念獲得）

児童生徒が直接タブレットの画面を操作し、概念の獲得や反復練習を行う教材です。余計なノイズを排し、直感的なドラッグ操作とブレのない即時フィードバックによって、自分の力で「できた」という内発的な達成感を積み上げさせます。

（掲載アプリ例：1対1対応 / 大きい・小さい / 数えよう / 平仮名キーボード / カルタ）

特別支援教育において、具体物を操作しながら学習することは非常に重要です。その考え方に基づくと、アプリでの学習はふさわしくないのではないかという疑念も生じますが、実践からアプリの意義を強く感じています。十分検証されていない内容ではありますが、アプリで概念形成の基盤を築き、具体物で概念を深めて汎化させるという指導の道筋も有効なのではないかと考えています。この内容については第2章以降で説明します。

### 2. 授業支援アプリ（視覚支援・集団共有）

教師が操作し、教室前方の大型モニター等に映し出し、学習内容やルール等を提示するためのツールです。従来PowerPointや画像、動画で提示してきた内容ですが、アプリを使用することでより柔軟な提示が可能となります。

（掲載アプリ例：スケジュール時計 / リズム視覚化ツール / 視覚支援動画プレイヤー）

児童生徒の操作を伴わないため、学習アプリより学習効率は落ちます。メインの学習手段ではなく、補助的ツールという位置付けが望ましいです。自分の好みや使用状況に併せてカスタマイズできるため、既存のツールより直感的で扱いやすいものができる可能性もあります。

### 3. プリント課題作成アプリ（教材自動生成・印刷）

児童生徒の実態に合わせて、最適な難易度・レイアウトのプリント教材を瞬時に自動生成して印刷できるアプリです。マス目のサイズ、問題数、数字の範囲等を調整するだけで、その日の授業にぴったりな個別課題を出力できます。

（掲載アプリ例：計算プリントメーカー / ひらがな単語プリントメーカー）

従来Excel等で作成していたプリントも、アプリ化することができます。問題の自動生成が大きな特徴で、児童生徒ごとに設定を変更して保存しておき、必要な児童の分だけ問題生成、印刷するということもできます。すでにマクロや計算式で問題を生成できるExcelファイルが存在する場合、わざわざアプリ化する必要はありません。プリントを新しく作成する場合には、アプリ化することも検討しても良いかもしれません。

### 4. 業務効率化アプリ（校務効率化・指導計画）

教員自身の事務負担や授業準備の労力を軽減、効率化するための実務支援ツールです。主指導計画の作成や、分掌業務の遂行のために、効率化できるツールを作成するというイメージです。指導計画の作成については、個別の指導計画、年間指導計画、単元計画等を関連付け、現状バラバラになっているファイルを一つのアプリに集約し、効率的に業務を進めるといったことも可能です。分掌業務については、教師の個に特化したツールとなりやすく、汎用性は低くなるかもしれません。

（掲載アプリ例：実態把握ツール / 自立活動流れ図）

# 第2章：学習アプリの5大メリットと具体物との使い分け

第1章では、生成AIを活用して様々なアプリを作成できることを紹介しました。では、なぜわざわざアプリを作る必要があるのでしょうか。本章では、具体物教材と対比しながら学習アプリの「5大メリット」を整理し、そこから見えてきた「概念の基礎形成における有効性（仮説）」と、具体物との役割分担について説明します。

### 本章の要点

・学習アプリの5大メリット：学習アプリには、学習効率を高める強みが大きく分けて５つあると考えています（1. 視覚活用の促進、2. 即時・一定フィードバック、3. 難易度調整、4. ノイズ除去、5. 反復学習の高密度化）。また、その他にもいくつかのメリットがあります。
・概念の基礎形成における仮説：物理的な具体物は情報（ノイズ）が多すぎるため、何に注目すべきかという点ではかえって曖昧（抽象的）になります。ノイズを削ぎ落としたアプリの方が、対象となる概念を直接的・具体的に捉えやすく、初期の概念形成や既存の経験の体系化において効率よく機能する可能性があります。
・具体物との役割分担と順序性：アプリだけで学習を完結させるわけではありません。また、アプリですべての概念を学習できるわけでもありません。アプリで基礎的な概念や学習の枠組みに触れ、その後に具体物で深めて現実世界へ汎化させていくという指導順序が有効な可能性があります。

## 2.1 なぜアプリが必要なのか？ ～学習アプリの「5大メリット」～

タブレット端末＋アプリでの学習には、様々なメリットがあります。それらのメリットを十分に生かすことで、より効率的な学習につなげたり、具体物のデメリットを補ったりすることができます。

【一覧表：学習アプリの5大メリット】

・1. 視覚活用の促進
→ 手探りでは操作できず、「見る必然性」を生み出す。また、見やすい環境も整っている。
・2. 即時・一定フィードバック
→ 即時判定。感情を排したブレのない評価により、正誤が明確。
・3. 難易度調整
→ 設定変更だけで瞬時にスモールステップ化。手軽な実態把握にも機能する。
・4. ノイズ除去
→ 約10インチの画面に学習の本質だけを絞り込み、余計な刺激を遮断する。
・5. 反復学習の高密度化
→ 自動生成と即時判定等により、同じ時間で具体物の2～3倍の問題数を学習できる。

#### 【各メリットの補足解説】

#### 1. 視覚活用の促進

具体物には凹凸や厚み、物とぶつかったときの音や固有覚フィードバックといった様々な情報が豊富にあるため、子供は目で見なくても手先の感覚だけでなんとなく操作できることがあります。また、一瞬ちらっと見て手探りで操作し、時間がかかってしまうこともよくあります。

一方、タブレットの画面には手掛かりとなる触覚情報が一切ないため、目で確認しなければ操作が成立せず、自然と「見る必然性」が生まれます。また、ノイズ除去とも関連しますが、具体物の手触りや動かすときの重み、音といったノイズが少ないことも、視覚の活用を妨げません。さらに、タブレット端末の画面サイズや位置も、負担が少なく見ることにつながります。概ね10インチのディスプレイにより、頸部の回旋や大きな眼球運動をせずに全体を見回すことができます。具体物の教材をこのサイズに収めようとすると、２cm程度のものをつまんだり離したり、位置の微調整をしたりすることが求められてしまいます。また、タブレットのベゼル（縁）は構造化と同じ効果を発揮し、発光する画面と併せて注目を促します。タブレットで学習する際は、必然的に視線が下向きになり、視野の大部分が机に遮られるということも、画面に注目しやすい要因となります。

このように、タブレット＋アプリは視覚活用を促すとともに、子供にとって見やすい環境が整っています。具体物も視覚化されたものではありますが、現実には子供は見ずに操作することも多く、その良さを生かしきれないことがよくあります。アプリで視覚化し、実際に視覚の活用を促すことで、よりわかりやすく、記憶に定着させやすい学習にすることができます。

#### 2. 即時・一定フィードバック

具体物の課題に取り組む場面において、ほとんどの場合教員が評価を行うこととなります。教員が対面で判定すると、無意識のうちに表情や声のトーン、視線、間などからヒントを与えたり、子供の感情の揺らぎにつながったりすることがあります。また、教員が他の子供に対応している間は指示待ち、採点待ちの空白時間が生じてしまいます。

アプリは即座に判定を行い次の問題へ進むため、待ち時間ゼロで学習を継続できます。評価が遅れた場合、次のようなことが生じ、学習を阻害する可能性があります。①注意がそれる：単純に別の対象に注意が向かい、評価された際に自分の行動（回答）と結びつかない可能性があります。②誤学習へとつながる：「正しい回答をする→◯を貰える」となるべきものが、「（正しい回答をするが評価を受けない）→離席する→◯を貰える」と、誤った学習をしたり、本来強化されるべき行動（正しい回答）が強化されないという事態に陥る可能性があります。③ワーキングメモリの弱さから、自分の回答に対する記憶が薄れる：回答後静かに待っていても、時間が経てば記憶が薄れ、強化の効率が下がる、あるいは強化されなくなる可能性があります。一方、即時フィードバックを行うことで学習が阻害されず、また、結果的に回答してフィードバックを受ける機会が増えるため、学習効率が上がる（強化されやすくなる）ことが期待できます。

即時フィードバックの意義は、行動分析学の「即時強化」の観点からも説明ができます。行動分析学では、ある行動の直後に強化（報酬）を与えることで、その行動が強化されると考えられています。逆に、強化が遅れると、強化の効率が下がることが知られています。行動から１秒フィードバックが遅れただけで、強化の効率が著しく下がるとも言われており、即時フィードバックの重要性が示唆されています。

また、ブレのないフィードバックは、子供にとって正誤判定が明確になり、強化（あるいは弱化）されやすくなるというメリットがあります。教員の経験や技量に左右されにくいというメリットもあり、一定レベルの指導を担保することにもつながります（※これは教員の関わりを排除するという意味ではありません。正誤判定という機械的な役割をアプリに任せることで、教員は「できたことを一緒に喜ぶ（強化の強度の向上）」「つまずきを観察する」といった内容に集中できるようになります）。

#### 3. 難易度調整

具体物教材で選択肢の数やステップを変えようとすると、その都度教材を作り直したり準備し直したりする手間が発生します。例えばパズル（分割パズル）を作成する場合、絵柄は３種類、分割数を２、４、９とすると、それだけで９通りの教材が必要となります。さらに、クラスの子供の数だけ用意するとなると、労力は計り知れません。

アプリであれば設定画面の操作だけで、選択肢等の数や出題する内容、ヒントの有無をその場で瞬時に変更できます。これにより、子供に適切な内容、難易度の課題を出題することができます。また、スモールステップで難易度を調整しやすく、わずかな変容を捉えやすくなる、一歩上の難易度に挑戦させやすくなる（難しければすぐに戻せば良い）、子供にとって飽きずに課題に取り組むことができるといったメリットが生じます。

また、難易度の細かな調整は、実態把握にも有用です。最低限の準備で課題を試すことができ、難しかったり簡単だったりすれば難易度を変え、さらに実態を確認するといったことを手軽に行うことができます。ただし、アプリでできたからといって具体物でもできるとは限らない、その逆もあり得るということに留意する必要があります。

#### 4. ノイズ除去

例えば、みかんの模型を使って数を数える学習をするとします。みかんを一つずつ枠内に移動させていきます。この時、模型の色や手触り、傷、色のグラデーション、みかんの個体差等、教材がもつ様々な情報を処理しながら学習を進めることとなります。また、移動させる際にもみかんの重さ、枠の中心からのズレ、みかん同士がぶつかった際のズレ、滑りや転がりへの注意等、様々な情報があり、それらを処理しながら学習を進めることが求められます。特別支援学校に在籍する子供は、こだわりや注意の過剰選択性があることも珍しくなく、数という学習の本質とは無関係な部分に気を取られてしまう可能性があります。

一方、アプリは基本的に平面のガラスの操作で完結し、手触りの変化や教材のズレなどは生じません。枠内に厳密に収める必要もなく、スナップ（自動的に特定の位置にそろえる）させることも可能です。教材を打ち付けて遊んだり積み重ねたりすることもできず、具体物と比べて遥かに少ないノイズ環境で学習を進めることができます。

また、約10インチの画面内に世界が限定され、視野が制限されることもノイズの低減につながります。これらのノイズ除去により、学習の本質だけに注意を向けさせやすくなると考えています。

また、これは極端な解釈かもしれませんが、３次元の物体である具体物を３次元空間で扱うということも、ノイズになりうるのではないかと考えています。アプリではx軸、y軸の動きで操作することが多く、z軸（高さ）という概念は基本的にありません。また、操作対象物の重なりも許容されます。一方、具体物では教材の厚みがあり、基本的に重ねることは想定されません。また、移動させて箱へ入れる際の高さといった情報も加わり、操作の負荷が増大することとなります。もちろん、最終的に３次元空間で学習の成果を発揮することが求められますが、概念形成の初期段階では、徹底的にノイズを除去し、身に付けさせたい概念に注意を向けさせやすい環境を整えることも効果的であると考えています。

#### 5. 反復学習の高密度化

具体物やカードを使った学習では、「教材を集める」「並べ直す」「片付ける」といった物理的な処理に時間を奪われます。あらかじめ準備しておくことも可能ですが、たくさん用意された教材は視覚的ノイズになる可能性があります。また、頑張って教材の入れ替えを速くしても、それ自体がノイズです。

アプリでは正解した瞬間に次の問題が自動生成されるため、物理的なタイムロスが極端に少なく、体感的には同じ時間内で具体物の2～3倍の問題数をこなすことができます。即時フィードバックでも触れましたが、こなせる問題数が増えることで、成功体験が増えたり記憶に定着させやすくなったりと、学習の効率が飛躍的に向上します。

【その他のメリット】

・保管が容易：web上、クラウド上に保存しておくことができるので、物理的に場所を取ることがありません。また、しばらく使わない場合でもデータさえ残しておけばいつでも使うことができます。HTMLファイルであれば、どんな環境でもおそらく相当長く使えるはずです。
・コピー、共有が容易：ファイルやURLを共有するだけで他者に共有できます。同じアプリを使用することで、共通のものさしとなり、実態を共有するのも容易になります。
・記録を残しやすい：アプリに簡単に履歴機能を入れ込むことが可能です。自分で記録を取らなくても、後から履歴を確認し、実態把握に役立てることができます。なお、同じドメイン上であれば、履歴を１箇所にまとめて確認することも可能です。

## 2.2 仮説：概念の基礎学習は具体物よりアプリの方が効率的ではないか

これら5つのメリットを活かしたアプリを実践する中で、一つの仮説をもちました。それは、「数の基礎や大小、平仮名の読み書きといった発達初期の概念形成においては、具体物から始めるよりもアプリを使った方が効率が良いのではないか」ということです。

一般には「具体物＝具体的でわかりやすい」「デジタル画面＝抽象的で難しい」と考えられがちです。しかし、子供、特に知的障害や自閉症スペクトラム等の障害をもつ子供の認知の視点に立つと、これは必ずしも正解とは言えない可能性があります。具体物は、色、形、重さ、手触り、音といった情報が含まれているため、「今、どの概念（大きさなのか、数なのか）に注目すべきか」という点においては極めて曖昧で、そこから本質を抜き出すという抽象化を子供に要求します。反対に、余計なノイズを削ぎ落として「大きさの違いだけ」「数の違いだけ」を直接提示できるアプリの方が、概念形成の初期段階においては「具体的」でわかりやすいという可能性を考えています。

また、ここでいう概念学習には、「未知の概念の基礎をゼロから学ぶ」ことだけでなく、「日常生活ですでに知覚・経験しているが、頭の中で整理されていないものを概念として体系化する」という側面もあります。実践の中で子供の反応を見ていると、以下の理由からアプリがこのプロセスを強力に後押ししていると感じます。

・ノイズ除去により概念そのものへ注意を向けさせやすい：こだわりや注意の過剰選択性の標的になり得る余計な刺激を削ぎ落とし、注目すべき属性だけに情報を絞ることで、子供が意識せずとも本質的な概念の方向へ注意を引っ張ることができます。また、具体物を移動させる際に生じる移動目標とのズレ、つまむ、持ち上げる、離す、倒れないようにする、止める等の身体操作を簡略化することも、ノイズの除去、あるいはワーキングメモリの負担軽減（空き容量の確保）につながるのではないかと考えています。
・構造化により言葉がなくても理解できる：画面上の枠組み（レイアウト）や動きの制限そのものが活動のルールを視覚的に示すため、言葉による説明の理解が難しい段階であっても、何をするべきかを直感的に把握できます。具体物でもある程度構造化し、活動のルールを視覚的に示すことはできますが、アプリではドラッグ中に枠に吸着させる等、具体物には無い動きが可能であり、偶然の動きからもルールを学習することが可能です。また、具体物でアプリのようなフィードバックを再現することは困難です。専門的な知識や技術、金銭的な負担が必要となります。
・フィードバックと難易度調整による「強化学習」の成立：操作に対して即座に一定のフィードバックが返ってくるため、サイクルを高密度に回すことができます。また、設定変更による細かな難易度調整が可能なため、偶然、あるいは自力で正解にたどり着ける絶妙なハードルを設定でき、試行錯誤を通じた概念の学習（強化学習）がスムーズに進みます。このことで、概念が形成されていない状態からでも成功体験を積み重ねることができ、概念の形成につながる、あるいは少なくとも活動のルールの理解にはつながり、後の学習に移行しやすくなると考えます。

なお、強化学習については後述します。

もちろん、この仮説がすべての概念に当てはまるわけではありません。たとえば「熱さ」や「硬さ」といった身体感覚を伴う概念は、基本的に具体物でなければ学べないと考えています。ただし、アプリを通して何を学ぶことができ、何ができないかという視点での研究は確認できておらず、安易に決めつけることは可能性を狭めることにつながりかねません。

## 2.3 具体物の不可欠性と「アプリから具体物へ」の使い分け

ここまでアプリの強みを述べてきましたが、アプリだけで指導を終えるわけではありません。画面上の操作は視覚と指先の動きに限定されるため、実際の物の質感や立体的な空間把握、力加減といった感覚情報は欠落します。また、アプリの画面内でできたとしても、それがそのまま日常生活のスキルとして直結するとは限りません。

具体物について、ノイズが多いということを述べてきましたが、現実世界ではそのノイズの中から必要な情報を抽出し、目的に応じて具体物を扱うことが求められます。アプリのみではこの学習は行えません。具体物は、学習と現実世界をつなぐために必須の教材です。具体物だけの学習も、逆にアプリだけの学習も、現代の子供たちには適しておらず、双方のメリットを活かして使い分ける視点が欠かせません。

そこで提案したいのが、従来の「具体物からデジタルへ」という順序を逆転させた、「アプリで基礎的な概念や枠組みに触れ、具体物で深めて汎化させていく」という役割分担です。

1. アプリで基礎概念と「学習の枠組み」を作る：まずは操作のハードルが低く、概念が直接的にわかりやすく提示されるアプリ環境で、「ドラッグして枠に入れる」「左側から順番に並べる」といった活動の基本ルール（行動の型）と基礎的な概念を身に付けさせ、人工的に「できる状態」を作ります。この段階で明確に概念が獲得できていると言い切ることは困難です。しかし、問題にランダム性をもたせ、学習させたい概念以外のヒントを除いた状態で高い正答率を残した場合、概念が獲得できていないと明確に否定することも困難です。
2. 同じレイアウトで具体物へ移行し、深めて汎化させる：アプリで迷わずできるようになったら、画面上の配置と全く同じレイアウト（同じ位置関係）で机の上に本物の箱や具体物を置いて学習します。その後、具体物やレイアウトを変化させていくことで、環境に依存しない概念が形成されていくのではないかと考えています。
実践例として、数えよう（基礎）のアプリで十分に学習した後、iPadの画面はホワイトボード、ドラッグする円は磁石、枠はペンで書くというようにし、アプリと同じレイアウトを再現しました。アプリからこの設定への移行はスムーズに行えることが多いです。その後、磁石をより立体的なもの（ブロック、食べ物の玩具）へ、枠を箱や手へと移行させていき、提示位置も変化させることで、「３ちょうだい」等の言葉で正しい数を取り出して渡すということができるようになりました。

このように、アプリで概念の基礎を作り、具体物で深化、汎化させていくという学習方法が有効なのではないかと考えています。

この「アプリから具体物へ」という順序性も、すべての学習内容やすべての子供に万能に当てはまるわけではありませんが、具体物での指導に行き詰まりを感じた際の極めて有効な選択肢になります。

# 第3章：アプリでの学習は、強化学習と似ている？

本章では、AIの機械学習の一つである「強化学習」を取り上げます。強化学習にはアプリを活用した指導と似た点が多くあります。もちろん、人間の学習とAIの強化学習は異なりますが、この仕組みをイメージすることで、アプリでの学習の中で子供に何が起きているのか、そしてアプリを自作する際にどのように設計すべきかという視点がわかりやすくなると思います。

### 本章の要点

・強化学習の基本サイクル：AIが試行錯誤とフィードバック（報酬・ペナルティ）を通じて、自ら最適なルールを獲得していく仕組みです。
・アプリ学習と似ている点：言葉による説明の理解が難しい発達初期段階において、子供がアプリを通じて活動のルールや概念を掴んでいくプロセスは、強化学習のイメージと重なります（ただし、あくまで教材設計のためのイメージを膨らませるものです）。
・適切な難易度と強化の頻度：広すぎる迷路では学習が始まらないのと同様、実際の学習場面でも「すぐに正解（強化）できる難易度」に調整することが大切です。
・不正解の扱い：不正解のフィードバックは、失敗を防ぐという観点から重要です。しかし、不正解の過剰な連続は、無気力、フリーズをもたらします。不正解を繰り返しすぎない配慮が大切です。
・「強化」という視点：単に◯☓を示すだけでなく、「正解という行動を強化する」という視点があれば、アプリを作成・活用する際に適切な難易度等の設定をイメージしやすくなります。また、完全に未学習の状態から概念形成をしていくための突破口が見えてくるかもしれません。

## 3.1 強化学習とは何か 〜迷路を進むAIの仕組み〜

まず、AIの機械学習の手法の一つである「強化学習」について簡単に説明します。

ここでは例として、「n × n マスの迷路を進んでゴールを目指すAI」を基に説明します。迷路の途中には入ってはいけないマス（火山）があり、そこに入るとペナルティが与えられます。

このAIは、最初から迷路の正解ルートを知っているわけではありません。右に進めばいいのか、左に進めばいいのかという知識もルールも持たない状態からスタートします。

AIは次のようなサイクルを繰り返します。

1. 状態の把握：自分が今どのマスにいるかを見る。
2. 行動：上下左右のどこかのマスへランダムに1マス動いてみる。
3. 結果（フィードバック）：

・ゴールに到達できたら、「報酬（プラスの得点＝強化）」を得る。
・入ってはいけないマスに入ったら、「ペナルティ（マイナスの得点＝弱化）」を受ける。
・（マイナスを避け、同じマスを行ったり来たりするだけにならないよう、１歩ごとに少しずつ「ペナルティ（マイナスの得点＝弱化）」を受ける）

言葉でルールを教え込まれなくても、この試行錯誤を何回も繰り返す中で、AIは「どのマスでどう動けば最も効率よく報酬を得られるか（＝ゴールできるか）」というルールを自ら学習していきます。

サンプルアプリ（強化学習シミュレータ）を実際に操作してみてください。迷路が狭ければゴールに辿り着く可能性が高く、すぐに道順を学習できます。迷路が広くなると、なかなかゴールにたどり着けません。数百回、数千回の試行が必要になるかもしれません。また、障害物（火山）の配置や数も学習に大きな影響を与えます。

## 3.2 アプリでの学習との類似性 〜思考の補助線としての強化学習〜

この強化学習の仕組みは、子供が学習アプリを使って課題に取り組む様子と非常によく似ていると考えています。

もちろん、人間の脳や感情の働きはAIの強化学習とは全く異なります。あくまでアプリのメリットを生かしつつ、質の高いアプリを作成するためのイメージとして捉えてください。

しかし、言葉による説明や抽象的な指示の理解が難しい子供が、アプリを操作しながら自力で活動のルールや概念の基礎を掴んでいくプロセスを考える上で、強化学習は非常に多くの示唆を与えてくれます。

迷路の話を、実際の学習課題に置き換えて考えてみます。例えば、「数字のカード（1、2、3）を順番に枠の中へ並べていく学習」を想定してみましょう。

・スタート地点：画面上に数字がバラバラに提示されている状態
・1マス進む（行動）：子供が数字を1つ選び、枠へ向かってドラッグする
・ゴール到達（報酬・強化）：正しい順番で枠に収まり、「ピンポン！」と正解音が鳴る
・進入不可マス（弱化・制約）：違う数字を置こうとしても枠に入らず、スッと元の位置に戻る

子供は最初から「数字の大小や順番」という概念を完全に理解しているわけではありません。画面を触り、動かし、返ってくるフィードバックを受け取る中で、「どう動かせば成功（正解）になるのか」という活動のルールを手探りで掴んでいきます。

## 3.3 適切な難易度と圧倒的な試行回数

強化学習のモデルから見えてくる重要なポイントのが、「適切な難易度設定」と「試行回数」です。

もし、AIにいきなり10×10 マスのような広大で複雑な迷路を与えたらどうなるでしょうか。AIは偶然にすらゴールにたどり着くことができず、報酬（強化）を一度も得られないため、どれほど時間をかけても学習が永久にスタートしません。

これは、子供の学習でも全く同じです。まだ数字の並び替えに慣れていない子供に、最初から「1から10までを順番に並べる」という課題を提示すると、途中で何度もやり直しになり、正解（強化）の達成感を一度も味わえないまま学習が停滞してしまいます。

そこで、迷路を2×2マスのようなごく小さなサイズに縮めます。アプリの設定で言えば、「選択肢を1と2の2つだけにする」ということです。1マス動かせばすぐにゴール（強化）に到達できる難易度にするからこそ、AIも子供も初めて「成功のサイクル」を回し始めることができます。このように、適切な難易度設定ができるようアプリを設計しておくことで、学習の効率を高めることができます。

そしてもう一つ欠かせないのが「圧倒的な試行回数」です。AIも1回ゴールできただけで迷路を完全に覚えられるわけではありません。何十回、何百回と成功を繰り返すことで、行動のパターンが強固に定着していきます。第2章で述べた「アプリによって教材の準備や片付けのタイムロスをなくし、具体物の数倍の反復を高密度に行う」というメリットは、まさにこの強化学習的な定着を成立させるために不可欠な要素です。具体物とアプリでは、同じ時間に取り組むことのできる問題数に差が出るため、アプリの方が強化しやすい（学習を効率的に進めやすい）可能性があります。

なお、実際の学習場面では「これ以上課題を簡略化できない」「障害物を取り除けない」ということがよくあります。このような場合、一つの突破口として「圧倒的な試行回数による学習」を進めるのも一つの選択肢になり得るかもしれません。当然、PDCAの観点は必要になりますが。

## 3.4 弱化（ペナルティ）の難しさと「動けなくなる」本質

学習を進める上で、「弱化（ペナルティ）」の扱いには慎重な配慮が必要です。

迷路において、入ってはいけないマスに入った時のペナルティは、「その選択肢を消去して無駄な探索を減らす」という意味で、学習効率を高め得る側面を持っています。実際のアプリでも、間違った場所に置こうとした際に「枠に入らず戻る」「☓印やブブーという音でのフィードバック」があることで、子供は「ここは違うんだな」と気付き、別の選択肢を試すことができます。

しかし、弱化には大きな難しさがあります。

現場でよく見られる「子供が課題の途中で手を止めてしまう、動かなくなってしまう」という状態について考えてみます。教員が感情的に怒ったり、極端に厳しい罰を与えたりしていなくても、この現象は起きます。その原因は罰の強さ（ダメージ）ではなく、「失敗（弱化）の頻度が高すぎること」、そして何より「成功（強化）に出会える回数が少なすぎること」にあります。

実際のAIの機械学習でも、ペナルティを与えられないよう、行動しないということを選択する例もあります。（これを防ぐために、時間経過や「何もしない」という行動をとった際にペナルティを与えるケースもあります）

したがって、子供が動けなくなるのを防ぐための本質は、弱化を完全にゼロにすること（エラーレス）ではなく、難易度調整によって「正解して強化を受け取れる頻度」を圧倒的に増やすことにあると考えています。十分な成功体験（高い強化頻度）という安心の土台があるからこそ、たまに生じる「元の位置に戻る」「☓印やブブーという音でのフィードバック」というペナルティが意欲を削ぐことなく、前向きな試行錯誤のための手がかりとして機能するのではないかと思います。

## 3.5 アプリ設計における「強化できるか？」という視点

強化学習のイメージを持つことの最大の価値は、アプリを自作する教員自身の中に、「このアプリで、子供を適切に強化できるか？」という明確な設計の視点（ものさし）が生まれることです。

単に「子供が楽しそうに触っている」「画面が動いている」というだけでは、効果的な学習教材とは言えません。

「子供が起こした行動に対して、ブレのない強化（即時フィードバック）が返っているか？」「子供の現在の実態に合わせて、成功（強化）の頻度が十分に高くなるような難易度設定やスモールステップが用意されているか？」「失敗ばかりが続いて強化が途切れてしまわないよう、手軽に難易度を調整できる仕組みがあるか？」「反復学習が保証されているか？」「学習させたい内容が強化されているか？」

このように、「強化」を軸にして教材を見つめ直すことで、アプリの画面構成や機能にどのような工夫が必要なのかが明確になってきます。

次章では、この「強化できるか」という視点やアプリのメリット、実践での気付きを踏まえ、子供の学習の効果を高めるアプリを作るための具体的な「設計思想」と画面づくりのポイントについて解説します。

======================================================================
第4章：特別支援教育における学習用アプリ 設計・実装思想
======================================================================
# 第4章：特別支援教育における学習用アプリ 設計・実装思想

アプリを作成する際、特別支援の観点、デジタル技術や端末の特性の観点、学習指導要領の観点など、考慮すべきことがたくさんあります。実践の中から見えてきた子供の操作の傾向も踏まえながら、画面構成や子供の操作などの考え方について説明します。ただし、特別支援教育においては幅広い実態や認知特性があり、だれにでも当てはまる正解は無いということにも留意が必要です。

### 本章の要点

・目的の明確化：対象となる子供の発達段階と学習目標を絞り込む。学習指導要領を基準に据えることで設計の輪郭が定まり、過度な汎用性による破綻を防ぐことができます。
・操作性の原則：概念学習初期は身体運動と結びつくドラッグ操作を基本とし、習熟後にタップへ移行する。スナップ吸着のタイミングや正解後ロックの使い分けが重要です。
・画面構成の構造化：操作対象（下部）と終点（上部）のコントラストと配置、非言語での視線誘導、重なり（z-index）への配慮、羞明や視認性を考慮した背景色選択を行います。
・端末特性への防衛：iPadのシステムスワイプ誤爆を防ぐ端40〜60pxの余白確保、Klee Oneフォントの活用、ダブルタップ拡大・スクロールの確実な禁止を講じます。
・ノイズ除去の徹底：指示文の削減、アニメーションや過剰な演出の抑制、不正解音や連打・不要なボタンへの対策により、注意の逸脱を防ぎます。
・AIの癖への対処と現場実装：AIが多用するマスの隙間・不要なヘッダー・過剰なカード枠や、終了時の消し忘れ・マルチタッチでの複製残留バグに対処し、HTML単一ファイル、左右分割設定画面、トリプルタップ等で現場防衛を図ります。

## 4.1 目的の明確化

アプリを作る際、まず「どんなアプリを作るか」を考えると思います。ここで大切になるのが、「どのような子供を対象に、どのような目標を達成させるためのアプリを作成するか」ということです。特に、発達段階についてのイメージは重要です。文字が読めない子供を対象としているのに読んで考える前提のアプリを作ったり、反対に学習が進み、定着を目指している子供に対して完全エラーレスのアプリを作っても効果は薄くなります。このようなことを避け、学習の効果を最大化できるようにするためにも、アプリの目的を明確にすることは重要です。

アプリの目的を検討する際に参考になるのが、学習指導要領です。単に「買い物」のアプリを作るということだけを決めても、具体的にどのような設計にするかイメージできません。特別支援学校学習指導要領知的障害の各教科小学部算数科第３段階を意図して買い物のアプリを作ろうと決めれば、自ずと設計は見えてきます。あるいは、算数科ではなく生活科を主とすることも想定され、その場合はアプリの設計は大きく変わってきます。

このように、基本的には各教科や自立活動の目標・内容を想定しながら作成していくのが望ましいと思います。自立活動においては、個々の実態の占める割合がより大きくなります。

付け加えると、「汎用性」という視点も検討すべき課題になってきます。「算数科２段階から、中学部数学科の１段階まで使えるアプリを」という設計も当然あり得る話です。子供にとっては、慣れ親しんだアプリで学習を継続させることができるため、新たな操作等を学習するコストを削減することができます。しかし、アプリを作成する側にとっては学習の順序をどうするか、難易度をどこまで細分化するか、同じようなレイアウトでステップアップさせても良いのか、厳密にはつながっていないのでは無いかと、思考のコストが跳ね上がります。不具合も発生しやすくなり、修正のコストも多くなります。そのため、「汎用性をもたせることが望ましいが、ある程度アプリ作成に慣れてから実施すれば良い」という考え方が良いのではないかと思います。対象となる子供、目標、内容を絞ることで、より細かな配慮のあるアプリとなることも期待できます。

## 4.2 操作性

### ① 操作はドラッグを基本、タップは慣れてから

型はめのアプリを想定します。画面上部に見本となる図形があり、下部に選択肢が並んでいます。このようなアプリでは、認知発達の観点から考えてもドラッグ操作の方が望ましいと言えます。理由としては色々ありますが、ドラッグによる操作は「感覚と運動の高次化理論」のⅣ水準の対応弁別に近く、タップはⅤ水準の対応弁別ポインティングに近いと説明することもできます。他にも、ドラッグすることで見本と選択肢を近距離で見比べたり、重ねたりすることができ、視覚的にわかりやすくなるという理由も考えられます。

また、別の観点として、具体物の教材には基本的にタップという操作はありません。今まで具体物を操作して学習してきたことを生かす、また、今後具体物を操作して学習するということにつなげるためにも、ドラッグ操作の方が望ましいとも言えます。

ただし、ドラッグ、タップ操作どちらにもメリット、デメリットが存在し、それらを考慮するという前提を忘れてはいけません。ドラッグ操作は直感的で分かりやすい反面、指の移動距離が長くなりがちで、操作に時間がかかります。私たちがスマートフォンで文字入力をする際、一文字ずつドラッグして文字入力欄に運ぶのでは時間がかかりすぎてしまいます。一方、タップ操作は指の移動範囲が狭く、操作時間は短縮されますが、デジタル特有の動きであり、直感的に分かりにくく、ある程度の認知発達を前提とするといったデメリットがあります。

### ② いろいろなドラッグ

ドラッグといっても、様々な種類があります。サンプルアプリ（画面下部の１〜３の数字カードを画面上部の□に順に並べる）を参考に説明します。

ーーードラッグ（画面にタッチして動かす）ーーー

・① 指（マウスカーソル）を中心として操作対象が追従する：基本的に使いません。時々AIがこのドラッグを採用してしまうが、操作対象の端に触れてドラッグしようとするとズレてしまいます。
・② 一般的なドラッグ（単一操作対象）：一つずつ操作させたいときに。数を１ずつ数えるなど。オススメ。
・③ 一般的なドラッグ（複数操作対象）：パズルなど。こだわりのある子供が、複数の対象を同時にハメようとすることがあり、見ていて面白いです。メリットはよくわかっていません。

ーーードロップ（操作の終わり）ーーー

・① 終点に近づいた時、自動で吸着（スナップ）する：学習初期にオススメ。適当に動かしても正解するため、何をすれば良いかを理解させるために使いやすいと思います。最初は適当に動かして吸着するということを繰り返していても、徐々に操作の方向が定まってくることが多く、結果だけでなく経過を見取ることが必要な段階です。
・② 終点に近づいた時、指を離すと吸着（スナップ）する：①の経験を十分に積んだ後にオススメです。明確な意図をもった操作が求められるため、教師にとって本当に理解して操作しているか把握しやすくなります。また、①ではドラッグ途中に別の枠に吸着してしまう事故も起きやすくストレスにつながりますが、それを防ぎやすくなります。

他にも、正解の枠にのみ吸着する、正解の枠以外で指を離した時、その場に留まる、元の位置に戻るといった設定も可能です。子供にとってわかりやすく学習が効率的に進む設定はどうなのか、答えは無いので実践を通して検討していくことが大切です。

ーーー（吸着後の操作）ーーー

ドラッグとは少し違いますが、吸着後の操作も併せて考える必要があります。

・① 正解後はドラッグ不能にする：正解に近付きやすくなります。強化学習をイメージするならこちらの設定の方がオススメです。
・② 正解後もドラッグ可能にする：実力テストのイメージ。なかなか正解までたどり着けないこともあるので、注意が必要です。

### ③ いろいろなタップ

ドラッグと比べると重要性は高くありませんが、タップにも種類があります。知っておくと使えるときがあるかもしれません。なお、厳密にはタップでは無いものも含みます。

・① 一般的なタップ（スマートフォン等）：対象に触れて、指を離したときに反応します。誤タップをして、指を離す前にずらすと反応しなくなります。タブレット等の操作に慣れていない子供の場合、タップしたまま指を離さず反応を待つことがあり、注意が必要です。また、Webアプリはネイティブアプリ（Storeから入手するアプリ）と比べて反応が悪いことがあり、「タップしたはずなのに反応しない」ということが発生しやすいです。
・② タップした瞬間に反応する：子供の身体操作、Webアプリの反応を考慮すると、この設定が一番オススメです。誤タップの頻度はやや増えるため、誤タップへの対応は検討する必要があります。
・③ ダブルタップ/トリプルタップ：基本的に使いません。設定ボタンを誤って開かないようにするといった用途で使用すると良いと思います。
・④ 長押し：③と同じく、基本的に使いません。トリプルタップは連打していれば偶然反応することがありますが、長押しは偶然の可能性が低いため、誤操作防止に効果的です。

### ④ ドラッグとタップの使い分け

これは本当に感覚的な話になってしまい、根拠の薄い内容になってしまいますが、大まかに「文字や数を学習する、あるいはそれ以前の段階はドラッグ中心」、「文字や数を活用して学習する段階ではタップに移行」というようにイメージしています。

### ⑤ 「できた/つぎへ」ボタン

操作対象をドラッグし終えたら自動で採点されるか、「できた」ボタン等をタップして採点されるようにするか検討する必要があります。また、採点後も自動で次の問題に移行するか、「つぎへ」ボタンをタップしたら次の問題に移行するかについても検討が必要です。

これらのボタンの使用/不使用はどちらにもメリット、デメリットがあります。自動採点は時間短縮、強化学習のイメージに適していますが、誤操作で不正解判定を受けてしまう可能性があります。できたボタンを使用する場合は、その反対になり、操作がやや複雑になるといったデメリットもあります。つぎへボタンを表示せず自動で次の問題に移行する場合も、時間短縮にはなりやすいですが、問題を振り返れないというデメリットが生じます。つぎへボタンを表示した場合は、その反対になります。

大まかな目安として、学習の初期段階はできた/つぎへボタンを使用せず、学習が進み自ら見直したり教師と振り返ったりすることが重要になれば使用するといったイメージが良いと思います。

## 4.3 画面構成

説明をしなくても感覚的にどうすれば良いかわかるレイアウト、構造化された画面構成を目指しましょう。そのためのポイントについてサンプルアプリを基に説明します。

### ① 操作対象と終点（ドラッグ先）の明確化

何を操作するのか、どこへ動かすのかといったことを視覚的に示すことが求められます。基本的には操作対象はイラスト、図形、文字等であり、注意が向きやすいものになることが多いため、過剰な装飾はあまり必要ないと思います。強調したい場合は、枠と少しの影をつけると浮き上がって見え、「これを動かす」とわかりやすくなります。

終点についても、基本的には枠で示すことになります。留意点として、枠のサイズを操作対象とそろえると、終点がわかりやすくなります。枠内は無色でも問題ないと考えていますが、枠内に色を付ける場合、薄めの色や灰色等を使用するとそこが終点だと認識しやすいようです。背景とのコントラストを上げようと、目立つ色や黒を使用すると、それ自体が操作対象と認識されてしまったり、終点と認識され辛くなったりする傾向にあります。また、配置も重要です。基本的には操作対象が画面下部、終点が上部にしておくと、手で終点が隠れにくくなるため操作しやすくなります。

また、後述のノイズ除去とも関連しますが、操作対象と終点を明確化するために、不要な情報を表示しないことも重要です。後述しますが、AIは文字での説明や枠によるセクション分けを多用する傾向にあり、知的障害のある子供にとっては情報量の多い画面になりがちです。不要な情報を削減することで、必然的に操作対象、終点が明確になります。

### ② 視線誘導

子供が画面を見る時、大まかに上から下という傾向があり、文字や数の学習をしていれば左から右という傾向もありますが、これは絶対ではありません。特に、発達初期の子供は左右の理解が進んでおらず、利き手に近い方に手を伸ばす、自分に近い画面下部から見るといったことも珍しくありません。学習を重ねることで、大人と同じように上から下、左から右といった見方になることを念頭に置く必要があります。

子供が明確に注目しやすいのは、イラストや色などです。そのため、意欲を高めようとキャラクターやカラフルな色彩で画面を飾り付けることは、学習の妨げになりかねません。画面をシンプルにし、注目させたい部分に色を付けるなどの工夫が有効です。

サンプルアプリを基に説明します。このアプリは線のなぞり書きです。

・① 文字でスタート、ゴールを示す。イラスト付き
・② 矢印でスタートを示す
・③ スタートに色を付けておく。スタートに触れた瞬間にゴールに色が付く

という構成になっています。当然、①が最もわかりにくく、③が直感的にわかります。このような工夫もアプリのルールの理解を促すために有効です。

### ③ 重なりへの対応（z-index）

具体物の教材では、操作対象が上下に重なることはあまりありませんが、アプリでは特別な設定をしない限り操作対象が上下（前面、背面）に重なってしまいます。これにより、操作対象が隠れたり、操作不能になったりすることがあります。これを防ぐために、前面、背面を表す「z-index」の調整が必要となります。z-indexの数値が大きいほど前面に、小さいほど背面に表示されるため、ドラッグしている最中のものはz-indexを大きく（最前面に）する、ドラッグ後は必要に応じてz-indexを小さく（背面に）するといった工夫が必要です。

### ④ 背景色とコントラストの選択基準（白 vs 薄グレー vs 黒）

背景色に明確な正解は無いと思いますが、考え方の参考として示します。

・ ① 白背景（標準・プリントへの接続）：
メリット：学校のプリントや教科書と同じ見え方のため、紙教材への移行に最も適しているかもしれません。明るい教室環境でも視認性が安定する。
留意点：画面全体が強く発光するため、羞明がある子には眩しすぎるかもしれません。
・ ② 黒背景（視認性の向上）：
メリット：コントラストを高めやすくなります。また、白背景に黒い文字よりも、黒背景に白い文字の方が視認性が上がる（弁別閾値が低くなる）と言われています。
留意点：「真っ黒（#000000）の背景に真っ白（#FFFFFF）の文字」を置くと、目が疲れやすくなります。黒背景を採用する場合は、文字や枠を少し落ち着いた薄グレーにするなどして、目への負担を考慮することが望ましいです。
・ ③ 薄グレー背景（羞明・眩しさへの配慮）：
メリット：画面全体の発光量を抑えつつ、上に置く文字や枠とのコントラストが「ちょうど良い強さ」に収まります。スマートフォンのライトモードと同じ配色で、少しだけ馴染みがあるかもしれません。
留意点：コントラストを高めにくくなります。枠を配置する場合、慎重に色を検討する必要があります。

## 4.4 端末の特性への対応

主にiPadでのアプリ使用を想定し、端末の特性と対応策について説明します。

### ① 画面端に操作するものを配置しない

タブレット端末では、画面下部から上にスワイプするとアプリを閉じる、画面上部から下にスワイプするとコントロールセンター等が表示されるという機能があります。画面の端に操作するものを配置しておくと、これらの機能が誤って起動してしまいます。大まかな目安として、40〜60px程度画面端から距離を置いて配置することが望ましいです。

### ② Googleフォント「Klee One」の活用

Windows端末にはUDデジタル教科書体が搭載されていますが、iPadには標準では存在しません。そのため、「さ」や「り」等、画と画がつながったフォントになってしまうことがあります。これを防ぐために、ライセンスフリーで教科書体に近い文字である「Klee One」を使用することが望ましいです。ただし、数字の「１」「７」のフォントにクセがあるので、その点については留意が必要です。

### ③ ダブルタップによる拡大、スクロールの禁止

Webアプリはブラウザで開くため、標準でダブルタップによる拡大が行われます。これにより正常な表示が妨げられるのを防ぐため、ダブルタップによる拡大の禁止を組み込む必要があります。また、標準では上下にスクロールが可能となっており、タップしたつもりがスクロール判定になってしまうこともよくあり、操作性が著しく損なわれます。拡大と同様、スクロールも禁止することで学習の中断を防ぐことができます。なお、スクロール禁止を命令すると、設定画面もスクロールできず、設定の下の方の項目にアクセスできなくなることがあります。設定画面のスクロール対応については別途指示が必要になります。

## 4.5 ノイズ除去

アプリのメリットとしてノイズを削減できることを挙げていますが、そのためにはノイズの少ない画面構成、操作性が必要です。考慮すべき点について説明します。

### ① 「文字による説明・指示文」の削減

AIが作成したアプリは、「ここにおいてね」等、文字での説明が多くなりがちです。必ずしも悪いという訳ではありませんが、これがノイズになり、注目させたい部分に注意を向けにくくなる可能性があります。また、文字のスペース分画面が圧迫されるので、文字を読ませることが目的に含まれないのであれば、「枠の形状」「色の手がかり」といった視覚的な支援を行い、文字による説明を省略することが望ましいです。逆に言えば、文字での説明が必要なアプリは構造化を検討する余地があるのかもしれません。

### ② アニメーションや過剰な演出の抑制

正解時の派手な演出、モーダル（画面上に現れる小さなウインドウ）、過剰な効果音によるフィードバック等は、課題への注意が逸れてしまう原因となります。フィードバックは画面を邪魔しない◯✕の表示や短い効果音を中心とし、学習課題そのものに注意を向けられるようにするべきだと考えます。

ただし、「点タップ」やなぞり書き等、あまり思考を必要とせずワーキングメモリを消費しない単純なアプリについては、意欲向上、集中力の持続を目的として演出を追加することも効果的です。

### ③ 不正解時のフィードバック

不正解時に「ブブ」という効果音を鳴らし、✕を表示したりドラッグしたものを元の位置に戻したりするのは、非常に分かりやすく有効です。ただし、その音や動きを気に入って遊んでしまうこともよくあります。そのような場合、効果音のオンオフ機能、不正解時の音を「カチッ」という無機質な音にする、不正解でも元の場所に移動させない等の設定が選べるようにしておくと、単なる遊びとして快を得るのではなく、「できた」という実感により快を得ることにつながりやすくなります。

### ④ 連打対策

「触ると音が鳴る」という因果関係を見つけると、本来の学習課題を放棄し、枠にはまったアイテムを猛烈に連打してカチカチ音を鳴らす遊びを行いがちです。一度正解したらドラッグできない、音が出ないという設定にし、注意が別の対象に向くことを防ぐ必要があります。

### ⑤ ボタン数の削減

基本的に、ボタンがあればまずタップします。ボタンの文字が読めなくても、ボタンと認識できる見た目であればタップします。わかりにくくしていても、教師が一度タップすれば真似してタップします。そして意図しない挙動により困る、パニックになるということがよくあります。この対策として、必要ないボタンは表示しない、ボタンの表示/非表示を設定できるように設計するといったことが有効です。

## 4.6 AIの傾向

AIの作成するアプリは、一定の傾向があります。これらは全てが悪い訳ではありませんが、全てをそのまま受け入れるのではなく、目的に応じて調整することが必要です。いくつか例を紹介します。
▲【実例図解】AIが生成するUIの4大傾向（①②は要調整・改善、③④は目的に応じた使い分け）

### ① 枠と枠の間に隙間（margin / gap）を空けて配置する

例えば平仮名の単語を書くアプリの場合、３文字であれば３つの□を表示します。AIの作ったアプリでは、その枠と枠の間に隙間ができることが多いです。また、高確率で枠は角丸の四角形になります。一般的なプリントでは正方形のマスがつながっているので、特に事情がなければプリントの形式に合わせる方が良いと思います。

### ② ヘッダーを配置する

画面上部にアプリのタイトルや「もんだい 1/5」といったヘッダーバーを配置する傾向にあります。問題数、正答数等を表示するのは問題ありませんが、このヘッダーが操作可能エリアを狭めてしまうことが問題となります。基本的にタブレットは横方向（横長）にして使用することが多く、上下の画面幅は貴重です。このヘッダーがあることで上下幅が圧迫され、一つ一つの枠などを小さくせざるを得なくなることもあります。ヘッダーを廃止し、問題数などは画面の右上、左上などに小さく表示することで見やすく操作しやすい画面構成とすることができます。

### ③ オブジェクト（画像など）をカード化する

りんごの画像を表示させる際、AIは画像をそのまま表示させず、四角い枠に影を付けて表示する傾向にあります。見やすく操作しやすいというメリットもありますが、枠の分だけスペースを圧迫するというデメリットもあります。また、可能性の話でしかありませんが、子供の中で「りんごを動かす」と「りんごのカードを動かす」というように差が生じるかもしれません。目的に応じて使い分ける必要があります。

### ④ 枠を多用する

カード化に関連して、AIは枠をよく使う傾向にあります。一つ一つのオブジェクトだけでなく、例えば選択肢の画像が３つあれば、その３つの画像が置かれているエリアにも枠を付けます。これが構造化として受け入れられるときもあれば、ノイズになったり余白が圧迫されたりすることもあります。これについても、目的に応じて使い分ける必要があります。

---

ここまでは画面デザインの傾向ですが、プログラムの動作（状態管理）の面でも、AIが作ったアプリには次の2つの不具合がよく起こります。

### ⑤ 問題終了後、オブジェクトが画面に残ってしまう（消し忘れ）

問題を最後まで解き終えて結果画面やホーム画面へ切り替わった後や、次の問題へ進んだ後に、前の問題で使っていた絵やカードなどのオブジェクトが画面に残ってしまうことがあります。これは表示切り替え時の「古いオブジェクトを消去・初期化する処理」をAIが単純に書き忘れているケースが多く、見た目の違和感や誤操作の原因になります。

### ⑥ ドラッグ中の別指タッチによるオブジェクト複製・残留バグ

オブジェクトをドラッグして動かしている最中に、別の指（もう片方の手など）でもともとオブジェクトがあった元の位置に触れると、オブジェクトが複製されたように新しく出現してしまうことがあります。さらに厄介なことに、先にドラッグしていた側のオブジェクトは参照の上書きなどによって処理がおかしくなり、指を離した（ドロップした）際のもとの位置に戻る・枠に吸い込まれる・消えるといった後処理がキャンセルされ、ページを更新（リロード）するまで画面上に一生残り続ける状態になります。

AIはPCのマウス（操作するカーソルが常に1つだけ）を前提としてコードを書く傾向があるため、子どもがiPadで両手や複数の指を使って操作した瞬間にこの問題が露呈します。対策として、ドラッグ中は1つの指（`pointerId`）だけを排他的に追跡して他のタッチを受け付けないようにし、指が外れたりキャンセル（`pointercancel`）されたりした時も確実に元の状態へ戻す設計を指示しておくことが重要です。

## 4.7 その他

上記以外にも、個人的にオススメする内容を紹介します。

### ① HTML１ファイルでのアプリ作成

通常WebページはHTML、CSS、JavaScript、画像、効果音などの様々なファイルにより構成されています。これらのファイルに対応したソフトウェア（VS Code等）があり、扱うための知識等があれば問題はありません。しかし、学校現場では自由にソフトウェアをインストールできません。また、知識がない場合は「どのファイルを書き換えれば良いのか」「フォルダ構成をどうすればいいのか」等、わからないことだらけになってしまいます。そこで、AIに単一ファイルで生成するよう命令すれば、管理も容易になり、コピペも必要なくなります。知識がゼロでもアプリを形にすることが可能となります。

ただし、ファイルを分割しない分、AIが全てのコードを出力する必要が生じ、生成に時間がかかったり、場合によっては出力の制限を超えてしまったりする可能性もあります。そのような場合は、ファイルを分割し、専用のソフトを使うことを検討しても良いと思います。

### ② アプリホーム画面の作成

スタートボタン、設定ボタン等を表示したシンプルなホーム画面を作成することを推奨します。後述の問題数の設定にも関わってきます。また、Webアプリの制約として、音声の読み上げ機能を使用する場合、必ず画面上のどこかのボタンを操作して読み上げのロックを解除しなければならないというものがあり、スタートボタンでロックを解除するようにしておけばその後の読み上げ等もスムーズに進むという理由もあります。

### ③ 子供の誤操作を防ぐ設定画面のトリプルタップ

子供は意図せず設定画面を開いてしまい、スライダーを動かしたりトグルをオンオフしたりしてしまうことがあります。これを防ぐためには、設定画面を開くボタンを目立ちにくくしたり、トリプルタップや長押しで開くようにしたりすることが有効です。教師目線では、長押しはめんどくさくトリプルタップの方が楽ですが、トリプルタップは突破されやすいです。より複雑な設定も可能ですが、教師にとっても面倒くさいです。「設定は勝手に変えない」というルールの指導という観点も大切だと思います。

### ④ iPadの横画面を活かした設定画面の左右分割

AIが作る設定画面は、多くの場合が画面中央の正方形のモーダルです。視認性が下がり、多くの設定項目がある場合はそれらを把握するのも大変になってしまいます。オススメの構成として、設定画面は全画面表示、左右分割レイアウトにし、左側は設定項目、右側は実際のプレイ画面のプレビューを表示すると、設定項目の説明を省略でき、使う側にとっても細かい説明を読まずにすむため楽になります。

### ⑤ 問題数の設定

「全◯問で終了し、ホーム画面に戻る」という設定をしておくと、アプリをやめられずにずっと続けてしまう子供でも区切りを付けやすくなります。反対に、学習に集中しにくい子供でも、終了までは頑張るという目標を設定しやすくなります。

### ⑥ 最終問題のみ効果音を変更

正解時のフィードバックとして、基本的にはシンプルな「ピンポン」等の音を推奨します。例外として、設定した問題数を終えたときは、ファンファーレのような目立つ音を設定することを推奨します。これにより、子供が達成感を味わえるだけでなく、教師が子供の学習の進捗状況を把握することができます。

### ⑦ 学習履歴の保存

アプリでの学習の履歴を残しておくことも容易です。指示によっては、問題数や正答数、間違えた回数や内容、文字を書くアプリであれば実際に書いた線をアニメーションで順に表示することなども可能です。子供が反復学習を行い、教師が後に学習の様子を評価し、次の指導を考えるということが可能になります。

### ⑧ LocalStorageを使ったデータ管理とデータ削除機能

設定や履歴等のデータは、基本的にLocalStorageという機能を使用して保存するのが便利です。学校現場の実態として、特に義務教育段階では端末を使い回すことがあるため、保存された情報を削除できるようにしておくと安心です。情報の削除については、ブラウザのキャッシュの削除でも行うことができます。

## 5.1 プロンプト例

以下のプロンプトをコピーし、【作成したいアプリの概要】を編集して使用してください。あくまで一例なので、自由に書き換えてください。

--- マスタープロンプト（開始） ---
特別支援学校の児童生徒が使うためのWebアプリ（HTML5/JavaScript）を作成してください。

【作成したいアプリの概要】
（※分からなかったり指定がなかったりする項目は空欄のままで構いません。Gemini側で使いやすく補完してください）
・アプリ名：［例：たべものタッチゲーム］
・アプリのテーマ・目的：［例：画面を流れる果物をタッチして捕まえる］
・画面の見た目・配置：［例：上にスコア表示、中央に大きな描画エリア］
・児童生徒の操作：［例：画面上を動く絵文字を直接タップする］
・フィードバック・演出：［例：タップ成功で「パチン！」と音が鳴り、星のエフェクトが出る］
・その他こだわり：［例：失敗してもゲームオーバーにならず、ずっと遊べる］

【必須の技術・UI仕様】
1. **ファイル形式**:
   - HTML、CSS、JavaScriptをすべて「1つのHTMLファイル」にまとめて出力してください。
2. **フォント指定**:
   - Google Fontsから「Klee One」を読み込み、アプリ全体（テキスト、ボタン等）のフォントに設定してください。
3. **視覚要素（画像ファイル不可・絵文字 / HTML5 <canvas> 活用）**:
   - 外部の画像ファイル（png, jpg等）は使用せず、視覚要素は「絵文字（Emoji）」、CSSグラフィック、またはHTML5の「<canvas> タグ」を使って描画・表現してください。
4. **音声処理（外部音声ファイル不可・Web Audio API活用）**:
   - 外部の音声ファイル（mp3, wav等）は一切使用せず、効果音・BGMはすべてWeb Audio API（オシレーター等）を用いてJavaScriptコード内でシンセサイズして再生してください。
5. **iPad対応（PWA / 画面拡大・文字選択・システム誤作動・マルチタッチ誤動作の防止）**:
   - 「ホーム画面に追加」して使えるよう、<head>内に以下のメタタグを含めてください。
     • <meta name="viewport" content="width=device-width, initial-scale=1.0, user-scalable=no">
     • <meta name="apple-mobile-web-app-capable" content="yes">
     • <meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">
   - **【誤操作防止】** ダブルタップやピンチアウトによる画面拡大を防ぐため、CSS（`touch-action: manipulation;`）およびJavaScript（`gesturestart` イベントのキャンセル等）でズーム動作を完全に無効化してください。
   - **【文字選択防止】** 画面の長押しで文字やボタンが青く選択されたり、コピー等のポップアップメニューが出たりしないよう、CSS（`user-select: none; -webkit-user-select: none; -webkit-touch-callout: none;`）をアプリ全体に適用してください。
   - **【システム誤作動防止】** 画面下端からのスワイプ（ホーム復帰）や上端からのスワイプ（通知・コントロールセンター）の誤動作を防ぐため、画面の最上部および最下部には操作ボタンやドラッグ対象を配置せず、上下に適切な余白（マージン）を設けてください。
   - **【オブジェクト残留・複製防止】** ドラッグ操作がある場合は `pointerId` 等で現在操作中の1本の指だけを排他管理し、ドラッグ中に別の指が元の位置や他の対象に触れてもオブジェクトの複製や処理の競合が起きないようにしてください。また、`pointercancel` 時も確実に元の状態へ戻し、問題終了・画面遷移・リセット時には生成したオブジェクトや一時要素を画面から漏れなく削除して残り続けないようにしてください。
6. **画面構成（スタート画面と設定ボタン）**:
   - アプリ起動時はまず「アプリ名」と「大きなスタートボタン」がある【スタート画面】を表示してください。
   - スタートボタンをタップするとWeb Audio APIのAudioContextを初期化・アンロック（準備）し、メインの操作画面に切り替わるようにしてください。
   - 教員用の設定画面（モーダルまたは別画面）を開くための「設定ボタン（アイコン）」は、この【スタート画面】上に配置してください。
   - 設定項目が多くなった場合でも確実にすべての項目を操作できるよう、設定画面内は上下スクロール（`overflow-y: auto;`）ができるようにしてください。
7. **誤操作防止（設定ボタンのトリプルタップ・干渉対策）**:
   - 児童生徒の誤操作を防ぐため、設定ボタンは「アイコンをトリプルタップ（3回連続タップ）」した時のみ設定画面が開く仕様にしてください。
   - **【重要】** 画面全体のダブルタップ防止処理と競合しないよう、設定ボタンには `pointerdown` イベントとタップの経過時間（例: 500ms以内に3回タップ）を用いた独立した連打判定ロジックを実装してください。
8. **設定データの永続保存（localStorageの使用）**:
   - 設定画面で変更した内容（難易度や問題リスト等）は、ブラウザを閉じても保持されるよう `localStorage` に保存・読み込みできるようにしてください。
   - 同一ドメイン内の他アプリとのデータ競合（上書き）を防ぐため、`localStorage` のキー名には必ず「このアプリ固有のプレフィックス（例: アプリ名_settings）」を付与してください。
9. **アクセシビリティ**:
   - タップターゲットは大きく押しやすいデザインにし、タッチ操作に最適化してください。
10. **完全なコードの出力（最重要）**:
    - 描画処理やJavaScriptも含め、コードを絶対に途中で省略（「// ここに処理を記述」など）せず、そのままCanvas上でプレビュー動作する完全なHTMLコードとして出力してください。
--- マスタープロンプト（終了） ---

📦 オプション３：データを書き出し・読み込みして他のiPadと共有する

１台の端末で作成した単語リストや画像データをファイルとして出力し、別のiPadに一括で取り込みます。

--- オプションプロンプト（開始） ---
【指示プロンプト】
別のiPadでも同じ教材データを使えるようにしたいです。 設定画面に以下の2つのボタンを追加してください。
「データを書き出す」ボタン：登録した画像や設定内容を1つのJSONファイル（画像はBase64形式）として端末にダウンロード保存する処理。
「データを読み込む」ボタン：書き出したJSONファイルを選択してアップロードすると、現在のIndexedDBにデータを取り込んで即座に反映する処理。
--- オプションプロンプト（終了） ---

運用のメリット: AirDrop等でJSONファイルを他のiPadに送り、別のiPadで読み込むだけで、全端末に同じ教材環境を配付できます。端末のブラウザキャッシュが消えた際のバックアップとしても機能します。

## 5.3 プロンプト解説

マスタープロンプトに含まれる各指示の背景にある、教育的配慮や技術的な理由を解説します。

・【作成したいアプリの概要】 / （アプリ名、テーマ、画面配置、操作、フィードバック等）
→ ◯ AIに教材の核となるアイデアを伝える部分 / ここを書き換えます。未定の項目は空欄でもAIが適当な値を補ってくれます。可能な限り具体的に記入したほうが、イメージに近い結果を得やすいです。なお、画面配置については、イメージ画像をプロンプトに貼り付けることも効果的です。
・1. ファイル形式 / （HTML、CSS、JSを1つのHTMLファイルにまとめる）
→ ◯ Canvas対応とファイル管理のトラブルを減らすため / 通常はこれらのファイルを別々に保存して連携させますが、使用する「Geminiの作業画面（Canvas機能）」でその場ですぐに動作確認（プレビュー）を行うには、1つのHTMLファイルにまとまっている必要があります。また、どのファイルを書き換えるか迷わないようにします。ただし、コードが長くなりすぎた場合、一つのファイルに収まらなかったり、無理に一つのファイルに収めようとして機能が削られたりすることもあります。その場合は、複数ファイルに分けることを検討してください。
・2. フォント指定 / （Google Fontsの「Klee One」を適用）
→ ◯ 読みやすさと教育的配慮のため / 教科書体に近いフリーのフォントを指定しています。文字の形を捉えやすく、特別な準備なしで全端末で同じ見た目になります。
・3. 視覚要素（画像ファイル不可） / （絵文字、CSS、Canvasで描画する）
→ ◯ 著作権保護、画像準備の手間とリンク切れを防ぐため / 勝手に外部の画像を使用して著作権を侵害することを防ぎます。また、外部画像を指定すると、画像の保存やパス設定が必要になります。OS標準の「絵文字」やコード描画に限定することで、追加素材なしですぐに視覚的な教材が作れます。なお、OSによって絵文字は異なるので注意が必要です。
・4. 音声処理（外部音声ファイル不可） / （Web Audio APIでコード内で音を合成する）
→ ◯ 著作権保護、音声ファイルの用意を不要にするため / 勝手に外部の音源を使用して著作権を侵害することを防ぎます。mp3ファイル等を用意させると作業手順が複雑になります。ブラウザの機能（電子音の計算合成）で「ピピッ」「パチン」といった効果音をコード単体で鳴らします。
・5. iPad対応（誤操作・拡大・バグ防止） / （viewport設定、拡大・文字選択禁止、残留・複製防止）
→ ◯ 授業中の「動かなくなった・変になる」トラブルを防ぐため / 児童生徒が画面を連打したときに画面が勝手にズームしたり、長押しで青い選択枠や「コピー」メニューが出たりするiPad特有の誤動作を完全に封じます。また、画面端からドラッグして意図せずアプリを切り替えたりコントロールセンター等が出たりするのを防ぎます。さらに、両手・複数指でドラッグ対象を触った際の複製・画面残留バグや、問題終了後の消し忘れも予防します。
・6. 画面構成（スタート画面） / （スタート画面の設置と音声アンロック、設定画面のスクロール許可）
→ ◯ iPadで確実に音を鳴らし、設定操作を担保するため / iPad（iOS Safari）の安全仕様上、ユーザーが画面を一度タップしないと音声再生が許可されません。スタートボタンを踏ませることで、確実に音が出る状態を作ります。また、全体でスクロールを禁止していても設定画面内はスクロール可能にしておくことで、設定項目が増えても操作不能になるトラブルを防ぎます。
・7. 誤操作防止（設定ボタン） / （トリプルタップ（3回連続）で設定を開く）
→ ◯ 児童生徒が設定を変えてしまうのを防ぐため / 1回タップやダブルタップだと誤って設定が開きます。3回連続タップという教員のみが知る操作にすることで、授業の進行を妨げません。
・8. 設定データの永続保存 / （localStorageと固有プレフィックスの使用）
→ ◯ 端末の電源を切っても設定を残すため / 難易度や出題設定をブラウザ内に記憶させます。また、プレフィックス（識別名）を付けることで、同じドメイン内で別のアプリを作ったときにデータが混ざって上書きされる事故を防ぎます。
・9. アクセシビリティ / （タップターゲットを大きくする）
→ ◯ 運動面の操作性に配慮するため / 指先の細かいコントロールが苦手な児童生徒でも、押し間違えずに意図した操作ができるようにボタンサイズを強制的に確保させます。
・10. 完全なコードの出力 / （コードを途中で省略させない）
→ ◯ コピー＆ペーストだけで完成させるため / AIはコードが長くなると「// ここにロジックを追記」と処理を省略することがあります。この記述をしていてもコードを省略する場合があるので、その場合は「フルコードを出力」と指示してください。
